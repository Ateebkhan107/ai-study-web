# Phase 5 representative integration release plan

2026-10-22. **Prepared, not executed.** No production service, real student account, production credential or private record is part of this plan. Local SET ROLE tests and mocked Clerk tests do not count as live integration passes.

Use a dedicated disposable Supabase staging project and separate Clerk development tenant, with synthetic emails/identities only. First verify the actual staging server is PostgreSQL 17.6; if unavailable, report the blocker rather than substitute 18. Provisioning/connectivity needs separate approval and an explicit URL/project allowlist. Use staging keys only, exclude production environment files, pin application/candidate hashes and leave every Zi generation flag off. Review hosted role authority and private watcher/default/extension behavior before installation.

Synthetic actors: signed-out visitor, Clerk student A/B, unenrolled student C, two institutes with separate teachers/admins, and service-worker instances W1/W2. Seed owned profiles, balances, historical duplicate/null/partial attempts, repeated PYQs, active/frozen goal periods, earned/unclaimed badges, all question/score types, and coaching enrollments. Preserve opening state and record only synthetic IDs in private evidence.

| Flow | Required assertions |
| --- | --- |
| Clerk and server authority | Valid A token maps to A regardless of supplied user IDs; signed-out/expired/forged/wrong-issuer tokens fail; Clerk outage cannot fall back to supplied identity. Verify middleware plus handler/action behavior. |
| Browser Supabase/RLS | Use actual anon/authenticated clients and the project's configured token bridge, if any; do not assume Clerk automatically supplies Supabase identity. Required public/owned reads work; cross-user/institute writes fail. TRUNCATE/MAINTAIN and protected table/column mutation remain denied. Test question-bank/source edits, not just balance edits. |
| Profile/signup/leaderboard | New Clerk onboarding/webhook/profile initialization creates one zero balance; concurrent initialization cannot overwrite earned XP, name or counters. Review `handle_new_user`/nested routines under actual RLS. Existing profiles, rank ties, cached views and sign-out/sign-in work. |
| Normal tests | Start, load, save, submit, result and review; MCQ/numerical zero/multiple-correct/unanswered/negative marking. DB grading ignores supplied score/correctness. Wrong-owner/session/source and changed-payload retry fail without revealing answers. Fractional score compatibility must be resolved before admitting such questions. |
| Distributed submission | W1/W2 in independent app processes submit the same session concurrently. Terminate W1 before SQL commit, and separately drop its HTTP response after commit. Retry from W2: one lifetime attempt, immutable result, one base/goal receipt. Direct old writer and old-worker fallback remain denied. |
| PYQ | Same-key retry is identical; changed payload is a safe 409. Fresh-key replay cannot repay or inflate verified badge counts. Distinct questions, retakes, empty choices, all supported marking shapes, partial-batch failure and refresh/reconnect are checked. UI result/reveal/cache shapes remain compatible. |
| Goals/streak | Cross-user requests and fabricated counts do nothing. Verified events commit with source/reward; frozen old periods remain unchanged. Test UTC rollover, missing callback, delivery limit/backlog, transaction failure, interruption and later reconciliation. Establish an operational retry/drainer with alerts before claiming eventual delivery. |
| Badges | Check every enabled staging rule/threshold/reward definition against the nine-rule matrix; unknown/malformed rules fail safely. Opening eligibility is preserved, historical holds do not pay, new distinct sources count once, and display equals claim stats. Concurrent badge claims and XP faults cannot split marker/receipt/payment. |
| Coaching LMS | Teacher creates/publishes a test; assigned A starts and submits; results/report association are correct and private. B from another institute and unenrolled C are refused. Retry via W2, partial answer/association failure, refreshed page and expired token recover safely. Review membership revocation during an active test and existing entitlement policy explicitly. |
| Dormant generated storage | Exercise existing store/start/save/submit/result DTOs with literal synthetic questions, without an AI/provider request. Generated sessions never become normal XP sources. Real browser generation entry points remain closed. |
| Hosted DDL/default/private routines | With authorized private inspection, verify actual event watchers/default expressions and function dependencies; fail on drift/permission errors. Test `increment_xp` invoker/amount/identity/RLS behavior only against synthetic staging rows. EXECUTE alone neither proves exploitability nor safety. Keep raw definitions out of public logs/reports. |
| Install and recovery | Wrong endpoint/version/operator/policy, role reachability, column grants, lock contention, mixed-track history and fractional penalties abort atomically. Back up, restore to another disposable staging database, compare records/ACLs/RLS/routines, replay saved submissions and verify conservation. Never restore over post-cutover production writes. |

Evidence per scenario: application/SQL hashes, exact server version/role/endpoint, actor type, sanitized request/result status, private synthetic row/receipt counts, and PASS/FAIL/SKIPPED. Capture browser/API/DB behavior together; screenshots alone do not prove persisted state. Store keys/tokens/private definitions outside logs and Git. A failed prerequisite or unexecuted case is not PASS.

Release sequence: private/catalog review and policy approval → staging authority/provisioning approval → exact candidate/prerequisite rehearsal → signed-in browser/API/LMS regression → backup/restore and old-worker drain rehearsal → production approval request with reviewable artifacts. No production action is authorized by this plan.
