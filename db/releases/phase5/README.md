# Phase 5 release candidate — preparation only

The only deployment entry point is **`20261022_phase5_integrity.sql`**. The numbered goal/cutover files are review components; do not execute them separately in production. The entry point combines bootstrap and cutover in one transaction, so an intermediate goal implementation is never visible to application writers. It is outside the automatic migrations directory and has not been executed against production.

This is a production-form candidate tested on synthetic PostgreSQL **17.6**, not an approval to deploy or a claim that the hosted operator prerequisites are available. Exact source/schema/private dependency review and product sign-off remain required. It does not provision roles, disable RLS, delete data, back-pay rewards or enable AI generation.

Prerequisites, in reviewed order:

1. Approve the historical policy and complete private dependency/source-writer inventory. Arrange maintenance, worker drain, restorable backup and monitoring.
2. Verify the existing 16-table maintenance correction and both creator-default corrections against fresh catalog evidence. These remain separate approval units. The candidate's protected write restrictions are additional to those proposals.
3. Install the separately reviewed dormant generated-storage migration (`db/migrations/20261016_zi_generated_tests.sql`) with application generation flags off. The candidate currently requires its tables and compatibility function. Do not run that older storage migration after the integrity cutover: it would replace the compatibility routine. No generation/provider call is part of this order.
4. An independently approved platform operation must provide `prepzii_integrity_owner`: NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, BYPASSRLS, no membership/SET path from browser/service/authenticator/old postgres roles. The migration operator must already have reviewed SET/schema/table/function-owner authority. The local superuser can meet these conditions; hosted `postgres` authority has **not** been established. Do not grant application ownership or elevate the operator to bypass a refusal.
5. Confirm the required table columns, uniqueness keys, existing RLS/policies, default expressions, event triggers, incoming references, and exact function signatures in representative staging. The candidate assumes ordinary protected tables owned by `postgres`. Existing private schemas cause a fail-closed stop; upgrading an already-installed contract needs a separate migration, not re-seeding.

Before execution, a separately approved operator supplies exact session settings: `prepzii.release_database`, `prepzii.release_operator`, `prepzii.release_data_directory`, `prepzii.release_port`, `prepzii.release_endpoint` (actual server address or `unix-socket`), and policy token `preserve-opening-no-retro-v1`. Missing/mismatched settings abort before mutation. The script never embeds a production URL/password. PostgreSQL must report `170006`. The token does not substitute for human approval.

The one-shot transaction locks public source/session/attempt/answer/XP/PYQ/badge/progress/institute tables before creating capture objects, then locks the newly created goal ledger before snapshot/seeding. The original profiles and histories are retained. It installs lifetime reservations, private receipts/transaction permits, additive reward RPCs, the compatibility wrapper, badge opening basis and historical holds. Direct runtime and column mutations are restricted. Effective inherited/SET-only privileges are verified before commit. Five-second lock timeout and bounded statement timeout cause rollback rather than partial cutover.

Additional preconditions refuse fractional active/published question penalties (the legacy score column is integer) and ambiguous mixed historical badge tracks. These require explicit compatibility decisions; no rounding, conversion or historical repair is hidden in this migration. The inactive score-schema issue cannot be deferred if such live questions exist.

After an approved cutover, verify committed object/ACL/source hashes, conserved balances, historical rows, source uniqueness and RPC ownership before enabling `PREPZII_INTEGRITY_CONTRACT_ENABLED` on new workers. Keep Zi flags off. Older workers/clients lacking the contract must fail safely or be upgraded; restoring direct grants is not a compatibility strategy. Check PostgREST schema-cache readiness in representative staging before release.

Rollback before commit is the entire transaction. After commit, pause writes and retain opening snapshots, registry and receipts; use a vetted contract-compatible application or forward repair. Do not drop ledgers, restore absolute XP writes, grant old direct mutations, or restore a stale backup over newer writes without approved reconciliation.

The fresh rehearsal runner is `src/lib/tests/phase5ReleaseRehearsal.mjs`; it uses only fixed local Unix-socket targets with endpoint/operator/version/data-directory/filesystem guards and fresh database names. It applies prerequisite corrections/storage, the **exact combined candidate in one call**, acceptance tests, `pg_dump`, and `pg_restore --single-transaction --exit-on-error` into a different empty synthetic database. It compares 35 tables plus owners, effective default-normalized ACLs, RLS, columns/default hashes, constraints and routine hashes, then verifies restored replay does not pay again. It never drops a database or resets retained evidence.
